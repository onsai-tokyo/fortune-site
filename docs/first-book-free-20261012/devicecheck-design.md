# DeviceCheck付与設計（141／v4）

Appleのquery/updateにはDBとの分散トランザクションがない。トークンは一時的であり、永続端末IDとして扱わない。
公式仕様：https://developer.apple.com/documentation/devicecheck/accessing-and-modifying-per-device-data

無料付与だけをDBのゲートで全体直列化する。受付UUID・認証アカウント・同じトークンのハッシュを先に保存する。Appleのbit0=false確認後、条件付きでwritingへ遷移し、その後にAppleをbit0=trueへ更新する。成功確認後、付与・クレジット・アカウントの利用記録・受付完了を単一DBトランザクションで確定する。購入・復元・有料注文はこのゲートを使わない。

応答喪失時は同じ受付ID・同じトークンで再試行する。bit0=trueなら付与を完了、falseなら再更新する。checkingは2分後に失効できる。5分経過したwritingは、次の開始・遷移・完了RPCで同じ全体ロック下にてindeterminateへ不可逆に移す。その受付の付与は以後禁止し、全体ゲートを解放して別ユーザーの受付を再開する。遅れて戻った古いプロセスもfinishで拒否される。

iOSは受付IDとトークンをアカウント別Keychainに保存する。別のトークンへのすり替えは禁止する。indeterminateは本人に確認保留と表示する。同じアカウントで新しい受付を作り直しても付与しない。アカウント削除時はAppleのbit0を消さず、受付の所有者をNULLにした墓標を残す。

残る制約：Apple更新の成否不明・トークン消失／失効時に、二重付与なしと自動の付与漏れゼロを同時に保証できない。5分後は本人だけ保留し、他ユーザーは継続できるが、保留の自動回復は未実装。運用調査が必要であり、無条件にgrantedへ変更したり端末ビットを解除したりしない。この制約を隠して要件達成・無料ON準備完了とはしない。

bit0の同一Developerチーム内の既存用途との衝突確認と、実端末テストが必要。bit1は変更しない。trial_enabledは初期false。DeviceCheck専用キーの登録だけでは本番設定・無料ONは行われない。
