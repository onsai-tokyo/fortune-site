## 本文と画面

正本JSONのSHA-256は `c59f2adfe1241306e3a8dfb994332e442edfacab462bcb765c8be1203439e336`。同梱157ファイルのハッシュ、3600件のID・インデックス・60分割データと正本の表示項目を照合した。タイトル・概要・恋愛／仕事／暮らしの本文は変更せず、必要な日柱の60件だけを読み込む。サーバーのキャッシュ上限は8日柱分。APIへ全3600件を返さない。

既存の年カード→詳細の構成を維持。詳細は承認本文3テーマと「対象期間と候補ラベル」。カードと詳細表紙に候補バッジを表示する。年の一部だけの候補は通年バッジにせず、詳細に期間を明記する。専門的な根拠・IDは画面本文に出さず、保存JSONの `annualCalculation` と `metadataRefs` に残す。

初期表示は現在年−15〜＋20年（18歳以降・対応期間内）。過去を追加する操作も同じ年間エンジンを使い、保存済み出生スナップショットだけから計算する。保存済みカードは自動で書き換えない。プロフィール変更は次の新規鑑定に適用する。

## 暦・判定

本文キーは0始まりの日柱・流年、表示IDは1始まり。年カードは1月〜12月ではなく、立春の瞬間から翌年の立春直前までを表す。出生の日境界はJSTの0時、節気はライブラリーの中国標準時を瞬間に変換。大運はYun sect 2、年途中の開始時刻で区間を分割する。対応する出生年は1952〜2100、日本標準時。表示年は2100まで。対応外は確認案内を表示し、旧ロジックの候補で穴埋めしない。

同梱R01・R02・W01を型付きの独立モジュールに移植。元データの調査用R01〜R12とは別。月単位の判定・従来のスコアは使用しない。真／偽／不明を保持し、候補だけを表示する。本文はAI生成経路を通さない。

同梱実装との差：出生時刻不明を確定の正午にしない。日の始めと終わりで年・月柱が同じ場合だけその柱を利用し、時柱と大運開始は不明のまま。欠けた柱が仕事条件や三合成立・年運の必要性に影響し得る場合も不明を保持する。保留を偽に変えないための保守的な扱い。年・月の境界以外でも出生時刻不明でラベルが減ることがある。

## 入力と保存

iOSの新規鑑定・オンボーディング・プロフィールに任意設定を追加した。

- `annualYunConvention`: female / male / 未選択
- `spouseConvention`: female_officer / male_wealth / 未選択
- `workContext`: employed / independent / student / 未選択

性別入力から自動選択しない。旧プロフィールは追加項目なしでも読み込める。未選択は旧リクエストと同じ形にし、進行中生成の復旧を妨げない。明示した設定は生成・保存スナップショット・入力署名へ伝える。就業状況は過去の在籍履歴を推定せず、今回の表示名にのみ使用する。

## 有効化・配信手順

1. 既存の多数の未配信変更を混ぜず、本番の `e770304` を基準に今回の差分を取り出して再検証する。
2. `backend` で `npm run build` と `npm run test:annual3600`。資産を含むdistが必要。`tsc` だけで配信しない。
3. バックエンド `ANNUAL_READING_ENGINE=catalog3600` で有効化。未設定・不正値は旧年間エンジン。性格用 `NARRATIVE_ENGINE=personality` は維持する。
4. 年間設定・表示を含むiOSをビルドしTestFlightへ配信する。
5. 新規鑑定で本文・候補・保存後再表示を確認する。旧保存カードは自動更新しない。

解除は `ANNUAL_READING_ENGINE` を外す。既存生成の再実行・保存結果の破壊は行わない。
