Web explicit snapshot saving — LOCAL IMPLEMENTATION ONLY

The user's approved policy:
- Keep a reading in memory while navigating or returning from another app.
- Do not automatically restore an unsaved reading after a new page session.
- Saving requires a linked account and an explicit Save button.
- Reset affects current input/reading/draft, not saved snapshots or purchased books.

Implementation:
New immutable web_reading_snapshots table; Web-only /api/web/reading/snapshots API.
Snapshots store whitelisted display text, not entitlements or AI source data.
POST validates the authenticated owner's source before insertion.
RLS additionally checks owner, non-anonymous status, and owned source/partner.
The narrow SECURITY DEFINER ownership predicate avoids changing source-table
privileges required by existing iOS APIs. Its search_path is fixed and PUBLIC
and anon execution are revoked. Source lookups through the service client
always include authenticated user_id as well as the source id.
No UPDATE privilege; repeat POST ignores identical source/content hash.
Account deletion cascades; partner deletion cascades coupled snapshots.
Deleting the underlying reading nulls source_id without losing saved display text.

Legacy limitation — release gate:
Old reading_saves records contain only keys, not saved text or revision IDs.
They are kept unchanged and shown separately as awaiting migration.
Do not reconstruct them from a different/new input or claim the original text
has been recovered. Decide how to identify and confirm old source revisions
with the owner before production rollout. Current local UI does not expose
legacy entries as though they were verified immutable snapshots.

Legacy transition (approved and implemented locally 2026-10-21):
- Keep all old bookmark rows unchanged; do not silently backfill from latest input.
- Present old keys as legacy entries, separate from new immutable snapshots.
- Let the user select/enter the relevant birth input, inspect the newly generated
  reading, then explicitly save that version. Explain it may differ from the
  original; never label a fresh calculation as restored original text.
- Do not remove the old bookmark as a side effect of saving the new version.
- If exact original preservation is required, stop until a verifiable source
  revision is identified; created_at alone is not proof of the original content.
- /books/legacy/:readingKey shows current candidate text, requires a confirmation
  checkbox, and uses save-only behavior (never toggles an existing snapshot off).
  A changed input/body remounts the confirmation form and clears its checkbox.
  Missing candidate does not offer a save action; it directs users to check input.
  The old save row is never deleted or updated by this flow.
- Synthetic browser checks passed: missing candidate, consent gating, failed save
  retry, saved confirmation, old saves endpoint read-only, existing snapshot flows.
  Frontend build and 131 frontend-related unit tests passed.

Data retention:
Generation still creates server-side reading records needed by existing APIs.
This change removes automatic display restoration, not those internal records.
Automatic cleanup/retention and its implications for linked books require a
separate policy; no deletion or schema changes to existing tables were made.
An interrupted generation may retain pending input in user-scoped sessionStorage
for explicit recovery. Completed readings are memory-only until explicit save.
Auth sessions remain persistent; no secret or report content is newly cached.
A browser discarding the whole page is a new session, not background refresh.
