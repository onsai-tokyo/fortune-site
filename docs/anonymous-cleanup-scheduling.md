# 匿名アカウント清掃の運用案（未設定・未実行）

## 今回の安全性修正

- 既定はdry-run。明示的な `--apply` だけが削除を許可する。未知引数・重複指定はエラー。
- 一覧を先に走査し、全候補のbook/grant保護照会を終えてからapplyへ進む。照会エラー・null・不正なcountなら削除せず中断。
- 匿名フラグtrueだけを対象とし、単にemailがない非匿名ユーザーを含めない。
- 最終ログイン（なければ作成日）が30日以上前の候補だけ。時刻が不正なら除外。
- apply時は各ユーザーを再取得し、匿名状態・最終ログイン・book/grantを再確認してから削除。途中の照会・削除失敗は以降の削除を止める。すでに成功した削除を巻き戻すものではない。
- 全ページを削除前に読むため、削除しながらAuthページ番号を進める取りこぼしを避ける。
- dotenvは注入済み環境を上書きしない。ログはモード・候補件数・削除件数等のみで、キー・メール・UID・本文を出さない。

## 将来の担当者用コマンド例（今回はどちらも未実行）

接続先を担当者が確認し、秘密は承認済み管理環境に安全に注入してからbackendで行う。秘密値を引数・チャットに入れない。

```sh
npm run users:cleanup-anonymous
npm run users:cleanup-anonymous -- --dry-run
# 永久削除なので対象と実行直前の承認が必要：
npm run users:cleanup-anonymous -- --apply
```

引数なしと--dry-runではAuth削除は呼ばれないが、実行すれば実DBへの一覧・保護照会は発生する。今回の検証はメモリ上のfake storeを使う単体テストだけで、実プロジェクトには接続していない。

## 自動化前にまだ必要なこと

**定期実行は引き続き推奨しない。** book/grant保護だけで既存iOSの購読・購入済み読みもの・他台帳を完全に保護できるか未検証。Storage等の消去範囲、30日保存の運用ポリシー、最大削除数・重複実行ロック・接続先の強制照合も別途合意・実装が必要。
再確認と削除の間の競合は完全には排除できない。まず対象基準と復元方針を定め、保護された管理端末で手動dry-runの件数確認から始める。

## 将来の実行方法候補

- 初期推奨：週1回の手動dry-run＋承認付き手動apply。追加ホスティングなし。今回端末cronや常駐秘密鍵は作らない。
- 自動化する場合は、既存の承認済みCIの週次ジョブを候補とする。日曜03:00 JSTは土曜18:00 UTC。concurrencyで重複を止め、npm ciで固定し、秘密は運用担当が保護環境へ登録する。CI無料枠・課金条件を設定前に確認し、無料とは断定しない。
- Render Cron等の有料サービスは今回は追加しない。既存本番ワーカーに清掃処理を混ぜない。

スケジュールの停止では削除済みアカウントは戻らない。今回はスケジュール登録・課金・実際のdry-run・削除を一切行っていない。
