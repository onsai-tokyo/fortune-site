## 3. テストアカウントと1冊付与

Webの通常導線で専用アカウントを1つ作り、出生情報を保存する。テスト用メールを登録し、実メールの8桁コードで確認する。UIとDBの所有者UIDが同じであることを運用担当が確認する。一般公開画面やチャットへUIDやトークンを貼らない。

初期値 `/api/books/status` のenabled、remaining、memberRemaining、purchasedRemainingを確認。**非会員かつremaining=0の専用アカウント**を使う。既存会員状態を変更して条件を作らない。

承認済みの管理者実行環境（環境変数は安全に注入済み）で、backendから一度だけ実行する。秘密をCLI引数に含めない。

```sh
npm run books:grant-web -- <テストUID> <公開前確認専用の一意な注文ID> 1
```

これは `src/scripts/grantWebCredits.ts` → `ai_book_grant_web`。同じUID・注文IDでの再実行は冪等だが、別注文IDは別付与になる。異常時に注文IDを変えて繰り返さない。

成功：remaining=1、purchasedRemaining=1、memberRemaining=0。注文IDに対応する付与・クレジットが1つ。表示の更新待ちだけで追加付与しない。

失敗：UID・注文ID・RPC結果を確認。誤付与時は同じテストアカウントのみを手順7で清掃、または管理者承認の個別失効を行う。実ユーザーの付与を削除しない。

## 4. 作成 → 本棚 → 届く

保存した本人読みものを選び、要件を満たす安全なテスト相談を書く。AIへの情報送信に同意して一度送信。operationIdを記録する。画面更新や一時切断から同じ操作が復帰すること、本棚で作成中のポーリングが続くことを確認。無関係な出生・相談データは使わない。

成功：ブックがqueued/generatingを経てdeliveredとなり、remaining=0、purchasedRemaining=0。1つのoperationIdに1冊だけ。documentのtitle・summary・answer・sections（heading/body/sourceId/quote）・actionsと根拠の読みものを表示し、他人の情報がない。

review_mode=trueではreview状態で待つのが仕様。管理者が当該テストbookIdだけを確認し、承認する。公開全体のreview_modeをテストのために変更しない。

```sh
npm run books:review -- show <テストbookId>
npm run books:review -- approve <テストbookId>
```

`show` は本文を表示するため、担当者の保護された管理環境のみで実行し、チャットや共有ログへ転記しない。

失敗：一定時間動かなければoperationIdの状態、ワーカー稼働、レビュー待ちを確認。新規操作で重複作成しない。failedならクレジット返却を確認し、画面の再作成を一度試す。leaseを手で書き換えない。続行不可なら手順7・8。

## 5. ブック質問2回

届いた同じブックで、AI同意のうえ安全な質問を2回送る。各質問のoperationIdは別にする。非会員・FREE_QUESTION_LIMIT=0のままで行う。

成功：開始questionsLeft=2 → 1回目完了で1 → 2回目完了で0。本文に沿った回答が保存され、再読込でも維持。ブック購入冊数は0のまま。3回目はUIで送信できず、管理者がAPIでも確認する場合はBOOK_QUESTION_LIMIT（409）でAI呼び出しを行わない。同じoperationIdの再取得・再送で回数が増えない。

失敗：questions/operations/:operationIdで状態を先に確認。完了応答不明で別operationIdを発行しない。failedの質問は回数を消費せず、月間予約も返ることを確認。月間ユーザー・全体枠やレート上限に達した場合、それを無効化して通さず中断する。

## 6. 冊数・回数の最終照合

成功：初期0冊 → 管理者付与1冊 → 作成後0冊。1冊が所有者の本棚にあり、質問2件がcompleted、残り0回、重複注文・ブック・月間予約がない。成功は画面だけでなく所有者条件付きAPI/管理側レコードとも照合する。

失敗：新規利用を止めてoperationId・bookId・注文IDで限定調査。返金・付与・月間利用台帳を一括変更しない。復旧判断が必要なら担当者へ。

## 7. 退会してテストデータを削除

永久削除であるため、担当者が専用テストUIDと削除対象を再確認し、実行直前に承認する。共有本番プロジェクトの他アカウントには触れない。Webの退会操作（DELETE /api/reading/account）を使う。
